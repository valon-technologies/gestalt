Workflow Steps Implementation Notes

2026-05-20 Review Iteration

  • Accepted the review feedback that manager validation must reject invalid stepOutput references outside when. Config validation already covered inputs, plugin input, and delivery input; REST/SDK-created targets now use the same rule.
  • Accepted the review feedback that TargetPlugin run filtering must match any plugin step, not only the first plugin step.
  • Accepted the review feedback that inherited deliverResultToCaller delivery is only valid when the final step is an agent turn. The inherited delivery template uses a local final placeholder, so it is rewritten to the actual final step ID before the target is stored.
  • Decided to remove deployment identity from the phase-2 host-action selector instead of validating it there. Definition binding is introduced in the later definition PR; keeping unused selector fields in the action-only PR created an authority contract that the host could not honestly enforce.
  • Trimmed author-facing WorkflowValue to seven roots: literal, object, array, template, runInput, signalPayload, and stepOutput. Removed signalMetadata and workflowContext from proto (reserved tags 7/8). Activation and event data are normalized into runInput or canonical signalPayload before evaluation (#2071).
  • Re-review found that phase 2 had reintroduced legacy core Target.Plugin and Target.Agent fields while the public phase-1 contract is already steps-only. Deleted the legacy core fields and removed the remaining manager/bootstrap branches that converted or authorized flat targets.
  • Reserved WorkflowValue.event and WorkflowValue.schedule in phase 2 as well. Those roots were only meaningful once definition activations existed and would have made phase 2's SDK surface disagree with the trimmed value-language plan.
  • Regenerated/updated SDK protocol outputs after the value trim. Buf's Rust remote plugin was rate-limited, so the Rust generated WorkflowValue oneof was patched mechanically to remove tags 10/11 until a full regeneration can be run.
  • Python generation had produced top-level from v1 import ... imports for some generated gRPC stubs. Rewrote those to package-relative imports to keep the checked-in Python SDK importable.
  • Follow-up review found two fail-open/edge-case issues in the phase-2 runtime. Host action callbacks now require an explicit __gestalt.workflow.step_actions__ permission entry, and nested stepOutput references in when guards now skip with missing_dependency when their source step was skipped.
  • Removed a duplicated workflow target clone block in an executable-provider test helper. The duplicate overwrote the deeper clone path and could shallow-copy agent message metadata.

2026-05-20 Phase 3 Rebase

  • Restacked the definition PR on top of the simplified phase-2 action selector. The selector now carries definition id and generation only in the definition PR, where the host can validate them against stored execution-reference authority.
  • Added source_definition_generation to execution references. Config-managed schedules and event triggers use provider-owned definition ids that are not parseable as workflow_definition:<id>:<generation>, so the generation has to be stored explicitly with source_definition_id.
  • Configured schedule/event definition bindings now include definition_generation. Host callbacks validate provider-supplied definition generation against this stored source generation.
  • Buf remote plugin generation hit a BSR rate limit while regenerating Rust stubs. Go, Python, and TypeScript were regenerated through Buf; the Rust message field was patched to match the proto after restoring files deleted by the failed clean-generation attempt.

2026-05-20 Phase 3 Re-review Cleanup

  • Removed the execution-reference-only definition manager path. Agent workflow.definitions.create/update/get/delete now routes through provider-backed ApplyDefinition, GetDefinition, and DeleteDefinition so there is one definition model.
  • Renamed the internal Go core/manager definition model from Deployment* to Definition*. Remaining create/update wording refers to system-tool operations or legacy schedule/event upsert requests, not the removed deployment model.
  • Changed ApplyDefinition ordering so the manager builds the binding first, calls ApplyWorkflowDefinition, then publishes the new execution ref only after the provider accepts the definition. This avoids exposing a new active generation before the provider has durable state for it.
  • Agent-created definitions now receive a default manual activation. That keeps the provider-backed definition valid without requiring the agent tool caller to learn the full activation model for the simple create/update flow.
  • Definition tool responses now include executionRef separately from provider definition id. The definition id is the author-facing object id used for get/update/delete/start/schedule, while the execution ref is the opaque authority id used for provider callbacks and tests.
  • Restacked on the phase-2 host-action fixes: action callbacks now fail closed without explicit step-action permissions, and nested when values that reference skipped step output now skip as missing_dependency.
  • Removed phase-3-only test/helper bloat: a redundant second target-label scan and a duplicate Steps slice clone. The runtime target clone helper now also deep-clones agent message metadata.

2026-05-20 Atomic Definition Apply

  • Deleted the public workflow-provider PutExecutionReference RPC. ApplyWorkflowDefinition now carries the normalized execution reference, so definition state and callback authority are committed by the provider in one operation.
  • Kept GetExecutionReference and ListExecutionReferences as provider read APIs because WorkflowHost still reloads stored authority for callbacks and manager list/get surfaces need ownership filtering.
  • Split the internal Go execution-reference interfaces into read-only ExecutionReferenceStore and mutable ExecutionReferenceMutableStore. The mutable method remains for local/config/test stores, not as a remote provider contract.
  • Defined superseding as part of provider apply: when a new definition authority generation is accepted, older refs for the same definition/schedule/event are marked revoked or otherwise made inert before ApplyWorkflowDefinition returns success.
  • Changed manager start and signal-or-start flows to require a definition id. The agent workflow system tool still accepts an inline target for convenience, but it first applies a manual definition and then starts that definition.
  • Updated fake providers to model the new atomic contract: failed apply does not publish a new execution ref, delete revokes existing authority, and stale generation callbacks are rejected by host-side ref reload/generation checks.
