Workflow Steps Implementation Notes

2026-05-20 Review Iteration

  • Accepted the review feedback that manager validation must reject invalid stepOutput references outside when. Config validation already covered inputs and plugin input; REST/SDK-created targets now use the same rule.
  • Accepted the review feedback that TargetPlugin run filtering must match any plugin step, not only the first plugin step.
  • Decided to remove deployment identity from the phase-2 host-action selector instead of validating it there. Deployment/definition binding is introduced in the later definition PR; keeping unused selector fields in the action-only PR created an authority contract that the host could not honestly enforce.
  • Trimmed author-facing WorkflowValue to seven roots: literal, object, array, template, runInput, signalPayload, and stepOutput. Removed signalMetadata and workflowContext from proto (reserved tags 7/8). Activation and event data are normalized into runInput or canonical signalPayload before evaluation (#2071).

2026-05-22 Output Delivery Deletion

  • Started a stacked cleanup PR on top of the step-target PR to remove the workflow step delivery side channel. The intended replacement is an explicit plugin step that references the prior step via stepOutput, which keeps side effects one-per-step and removes special retry/failure semantics.
  • Kept WorkflowHost.InvokeOperation for this slice. Temporal and IndexedDB providers still depend on it for whole-target execution; deleting that callback path requires provider-side step interpretation or a normal SDK/API replacement for all plugin and agent steps.
